## 一、潛在 BUG（P0：必須立即修復）

### BUG-1：`StorageService.load_data` 方法不存在

- **檔案**：[project_controller.py](file:///c:/Users/yenfu/OneDrive/JiuFangTKC/655.AI_agent/Jiufang_Novel_Editor/controllers/project_controller.py#L653)、[autosave_controller.py](file:///c:/Users/yenfu/OneDrive/JiuFangTKC/655.AI_agent/Jiufang_Novel_Editor/controllers/autosave_controller.py#L94)
- **問題**：兩處呼叫 `StorageService.load_data(file_path)`，但 [storage.py](file:///c:/Users/yenfu/OneDrive/JiuFangTKC/655.AI_agent/Jiufang_Novel_Editor/services/storage.py) 中只有 `load_project_from_json` 方法，`load_data` 從未定義。
- **影響**：當使用者嘗試讀取舊版 JSON 暫存檔時，會觸發 `AttributeError`，導致載入失敗。由於外層有 `try-except`，錯誤會被靜默吞掉，使用者只會看到「暫存檔為空或格式無法辨識」的誤導訊息。
- **修復方式**：將兩處 `StorageService.load_data(file_path)` 改為 `StorageService.load_project_from_json(file_path)`。

### BUG-2：全書自動排版使用錯誤的節點類型判斷欄位

- **檔案**：[editor_controller.py](file:///c:/Users/yenfu/OneDrive/JiuFangTKC/655.AI_agent/Jiufang_Novel_Editor/controllers/editor_controller.py#L211)
- **問題**：`open_auto_format_dialog` 的 `process_item` 內部使用 `data.get("is_folder", False)` 來判斷是否為資料夾節點，但 UserRole data 中實際的欄位名稱為 `"type"`（值為 `"folder"` / `"file"` / `"scene"`），不存在 `"is_folder"` 欄位。
- **影響**：`data.get("is_folder", False)` 永遠回傳 `False`，導致 folder 節點也會被嘗試排版。folder 節點的 `content` 通常為空字串，因此實務上不會產生嚴重損壞，但邏輯不正確。
- **修復方式**：改為 `data.get("type") == "folder"`。

### BUG-3：`save_temp_doc` 呼叫路徑不一致

- **檔案**：[stats_controller.py](file:///c:/Users/yenfu/OneDrive/JiuFangTKC/655.AI_agent/Jiufang_Novel_Editor/controllers/stats_controller.py)（L178、L189、L221、L332）
- **問題**：`StatsController` 內部呼叫 `self.mc.save_temp_doc()` 而非 `self.mc.project.save_temp_doc()`。雖然 `MainController.save_temp_doc` 只是委派給 `project.save_temp_doc`，兩者功能等價，但這違反了其他所有 Controller 統一呼叫 `self.mc.project.save_temp_doc()` 的慣例。
- **影響**：功能上目前無問題。但若未來 `MainController.save_temp_doc` 被移除或修改行為，這些路徑會斷裂。
- **修復方式**：統一為 `self.mc.project.save_temp_doc()`。

## 二、技術債（P1：應儘快處理）

### DEBT-1：殭屍欄位 `paste_large_count` / `delete_large_count`

- **問題**：根據移除刪貼行為監控的開發歷程，`StatsController.on_text_pasted` 和 `record_text_modification` 已被清空為 `pass`。但整條資料鏈仍殘留：
  - `models.py` 的 `WritingLogEntry` 仍定義 `paste_large_count` 和 `delete_large_count` 欄位
  - `database.py` 的 `writing_logs` 資料表仍包含這兩個欄位
  - `database_migrations.py` 仍有 v11->v12 的遷移邏輯
  - `writing_chart_view.py` 的 `set_data` 仍接收 `total_paste_large` 和 `total_delete_large` 參數
  - `main_controller.py` 的 `get_writing_logs_as_dict` 仍序列化這兩個欄位
- **影響**：增加維護成本與認知負擔。新開發者會誤以為此功能仍在使用中。
- **修復方式**：
  1. 從 `WritingLogEntry` dataclass 移除兩個欄位
  2. 從 `writing_chart_view.py` 移除相關參數
  3. 保留資料庫欄位與遷移腳本（向後相容），但在 `get_writing_logs_as_dict` 中停止序列化
  4. 移除 `on_text_pasted` 和 `record_text_modification` 兩個空方法

### DEBT-2：三處重複的「依 ID 查找 TreeWidgetItem」邏輯

- **問題**：以下三個位置各自實作了幾乎完全相同的遞迴查找函式：
  - `tree_controller.py` L799：`find_item_by_id`
  - `search_controller.py` L355：`_find_tree_item_by_id`
  - `card_controller.py` L723：`_find_tree_item_by_id`
- **影響**：程式碼重複、修改時需同步三處。
- **修復方式**：統一由 `TreeController.find_item_by_id` 提供，其他 Controller 透過 `self.mc.tree.find_item_by_id(item_id)` 呼叫。

### DEBT-3：`save_temp_doc` 委派鏈過長

- **問題**：`save_temp_doc` 的呼叫鏈為：
  ```
  各 Controller → mc.project.save_temp_doc()
                → mc.autosave.save_temp_doc()
                → DatabaseService.save_project(...)
  ```
  但 `MainController` 自身也有一個 `save_temp_doc` 方法只做 `self.project.save_temp_doc()`，加上 `StatsController` 呼叫 `mc.save_temp_doc()`，形成兩條平行路徑。
- **修復方式**：保留 `MainController.save_temp_doc` 作為唯一入口，所有 Controller 統一呼叫 `self.mc.save_temp_doc()`，而非直接觸碰 `self.mc.project.save_temp_doc()`。或反過來，移除 `MainController.save_temp_doc`，所有 Controller 統一呼叫 `self.mc.project.save_temp_doc()`。二選一即可，但必須統一。

### DEBT-4：`except Exception` 過度使用（48 處）

- **問題**：全專案共 48 處使用 `except Exception` 或 `except Exception as e`，其中多數僅 `print` 錯誤訊息後靜默繼續。
- **影響**：隱藏了真正的 Bug（例如 BUG-1 的 `AttributeError` 被靜默吞掉）。除錯時無法快速定位錯誤來源。
- **修復方式**：分批改進：
  1. 關鍵路徑（儲存、載入、匯出）改為捕獲具體例外（`FileNotFoundError`、`sqlite3.Error`、`json.JSONDecodeError`）
  2. 保留 `except Exception` 作為最外層兜底，但加入 `logging.exception()` 取代 `print`
  3. AI 網路呼叫等容錯性高的場景可保留現狀

### DEBT-5：大型 View 檔案缺乏拆分

- **問題**：
  - `right_panel_view.py`（696 行）：包含右側面板所有分頁的建構邏輯，涵蓋卡片分類區、幕屬性區、等多個功能區塊
  - `writing_log_dashboard.py`（522 行）：混合了佈局邏輯與圖表資料處理
  - `ai_scope_dialog.py`（490 行）：AI 範圍選擇對話框，含複雜的樹狀結構操作
- **修復方式**：將各檔案按功能區塊拆分為獨立 Widget 元件。例如 `right_panel_view.py` 可拆為 `card_tab_view.py`、`scene_info_tab_view.py` 等。

## 三、功能連結缺失（P1：影響使用體驗）

### LINK-1：`execute_global_search` 呼叫了不存在的 `self.mc.editor` 屬性別名

- **檔案**：[search_controller.py](file:///c:/Users/yenfu/OneDrive/JiuFangTKC/655.AI_agent/Jiufang_Novel_Editor/controllers/search_controller.py#L245)
- **問題**：L245 呼叫 `self.mc.editor.save_current_editor_content()`。`self.mc.editor` 是 `EditorController` 的實例。但 `MainController` 本身也有 `save_current_editor_content()` 方法（同樣委派給 `editor`）。這裡直接呼叫 `self.mc.editor.save_current_editor_content()` 雖然能運作，但與其他地方統一使用 `self.mc.save_current_editor_content()` 的慣例不一致。
- **修復方式**：統一為 `self.mc.save_current_editor_content()`。

### LINK-2：大綱視圖（OutlineView）未即時同步新增/刪除/重新命名操作

- **檔案**：[tree_controller.py](file:///c:/Users/yenfu/OneDrive/JiuFangTKC/655.AI_agent/Jiufang_Novel_Editor/controllers/tree_controller.py)
- **問題**：`convert_tree_node` 中（L390）有條件地更新 `outline_view`，但 `add_tree_node`、`add_scene_node`、`delete_tree_node`、`rename_tree_node`、`move_item_up/down` 等操作均未同步更新大綱視圖。
- **影響**：若使用者在大綱視圖開啟的狀態下進行樹操作，大綱顯示的內容會過時。雖然切換回大綱頁時會重新填充，但即時性不足。
- **修復方式**：在每個樹操作結束後，檢查 `center_stack.currentIndex() == 3`，若是則呼叫 `outline_view.populate_from_tree(...)`。

### LINK-3：垃圾桶中的項目於快照（Snapshot）時不被保留

- **問題**：`trash_bin` 存放的是 `QTreeWidgetItem` 的直接引用（記憶體物件）。快照（Snapshot）系統對章節樹進行序列化時，不包含垃圾桶內容。當使用者還原快照時，垃圾桶中的項目會遺失。
- **影響**：若使用者刪除章節後建立快照、再還原快照，被刪除的章節既無法在樹中找到，也無法從垃圾桶復原。
- **修復方式**：快照序列化時一併保存 `trash_bin` 內容，或在還原快照前清空垃圾桶並提示使用者。

## 四、專案精簡建議（P2：長期優化）

### SLIM-1：評估是否仍需保留 `StorageService`（JSON 讀取）

- **現狀**：`StorageService` 已被標記為 `DeprecationWarning`，僅用於極早期 JSON 專案遷移。
- **問題**：若所有使用者均已遷移至 SQLite 格式，此模組可完全移除。同時需刪除 `autosave_controller.py` 和 `project_controller.py` 中的 JSON 載入分支。
- **建議**：確認是否仍有使用者持有 `.json` 格式專案檔。若無，可安全移除整個 `storage.py` 及其引用。若仍有，保留但不投入維護資源。

### SLIM-2：`writing_chart_view.py` 與 `writing_log_dashboard.py` 合計 975 行

- **現狀**：兩個元件功能高度耦合（dashboard 內嵌 chart_view），但分散在兩個獨立檔案中。
- **問題**：`writing_chart_view.py` 自行管理資料處理邏輯（日期分組、累加計算），這部分應屬於 Service 層或 Controller 層。
- **建議**：將資料處理邏輯抽到 `StatsController` 或新增 `WritingLogService`，讓 View 純粹負責渲染。

### SLIM-3：`ai_service.py` 單檔 928 行

- **現狀**：包含 `AIService`（設定讀寫）、`AIWorker`（背景 API 呼叫）、`AIContinuationWorker`（續寫）、`AIStreamWorker`（串流）等多個類別。
- **建議**：拆為 `ai_settings_service.py`（設定讀寫）與 `ai_worker.py`（所有 QThread Worker 類別）。

### SLIM-4：Theme 模板字串過長（`theme_manager.py` 667 行）

- **現狀**：CSS 模板字串佔了約 500 行。
- **建議**：將 CSS 模板提取至外部 `.qss` 檔案或 `themes/` 目錄下的 JSON/YAML 設定檔，`theme_manager.py` 改為讀取檔案並填充變數。可大幅縮減程式碼行數，並讓主題更易於維護與擴展。

## 七、總體評價
