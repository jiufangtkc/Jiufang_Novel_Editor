# 九方小說編輯器：長文分析引擎工程規則

## 1. 專案目標

本專案是一套小說編輯器，使用者希望透過本地 Local LLM，
分析約五、六萬字的小說，抽取人物、事件、地點與關係，
並建立可供作家使用的人物資料卡片。

主要使用情境：

- Local LLM。
- 小模型。
- 約 8K context。
- 長篇小說。
- 分段分析。
- 結構化資料。
- 人物卡片。
- 可恢復的長時間分析工作。

## 2. 最高優先級：系統穩定性

任何長文分析工作都不得以犧牲整台電腦的可操作性為代價。

特別注意：

- UI 不得被長時間工作阻塞。
- 不得存在無限制迴圈。
- 不得存在無限制遞迴。
- 不得存在無限制重試。
- 不得存在無限制資料成長。
- 不得存在無法取消的長時間任務。
- 不得存在取消後仍持續執行的背景任務。
- 不得在未確認原因前，擅自增加並行數。
- 不得在未確認原因前，擅自增加 context。
- 不得在未確認原因前，擅自改用更大的模型。

如果發現可能造成系統卡頓的問題，
優先修復穩定性，而不是提高分析品質。

## 3. 禁止大規模重構

除非使用者明確批准，
不得一次重寫整套長文分析引擎。

每次修改必須：

1. 只處理一個明確問題。
2. 說明修改原因。
3. 說明影響範圍。
4. 執行對應測試。
5. 回報測試結果。
6. 確認沒有破壞原有功能。

## 4. 必須先診斷，再修復

當使用者回報長文分析造成系統卡頓時，
不得直接提出新的長文分析演算法。

必須先：

1. 閱讀現有程式碼。
2. 建立分析流程地圖。
3. 找出所有 LLM 呼叫。
4. 找出所有背景任務。
5. 找出所有同步等待。
6. 找出所有重試與迴圈。
7. 找出所有資料庫與檔案 I/O。
8. 找出所有可能阻塞 UI 的地方。
9. 建立最小可重現測試。
10. 建立資源監控。

## 5. 證據優先

所有問題判斷必須區分：

- 已確認。
- 合理懷疑。
- 尚未確認。

不得把猜測寫成結論。

不得因為 CPU、RAM、GPU 使用率沒有滿載，
就直接排除 I/O、等待、死結、分頁或其他系統問題。

## 6. 長文分析架構原則

長文分析不得依賴一次將整篇小說塞入 LLM。

優先考慮：

- 分段。
- 逐段抽取。
- 結構化資料。
- 人物合併。
- 人物卡片。
- 必要的跨段驗證。
- 失敗段落重跑。
- 中途取消。
- 中途恢復。
- 增量更新。

不得設計成：

「每分析一段，就重新分析前面所有內容。」

不得設計成：

「每分析一段，就重新建立整份人物資料。」

不得設計成：

「每分析一段，就重新掃描整本小說。」

## 7. 任務管理原則

所有長時間分析工作都必須具備：

- 明確的任務狀態。
- 明確的進度。
- 明確的取消機制。
- 明確的錯誤處理。
- 明確的逾時機制。
- 明確的重試上限。
- 明確的失敗恢復方式。
- 明確的資源使用紀錄。

## 8. UI 與背景工作

長時間工作不得直接阻塞 UI 執行緒。

但不得只因為「放到背景執行緒」就宣稱問題已解決。

必須同時考慮：

- CPU。
- RAM。
- GPU。
- 磁碟 I/O。
- 執行緒等待。
- 任務佇列。
- LLM 請求。
- 資料庫操作。
- 取消機制。

## 9. 測試原則

任何涉及長文分析的修改，
都必須先建立或更新測試。

至少要能測試：

- 少量文字。
- 多段文字。
- 完整分析流程。
- LLM 呼叫失敗。
- LLM 呼叫逾時。
- 使用者取消。
- 中途恢復。
- 失敗段落重跑。
- 重複執行。
- 大量資料。
- 資源限制。

不得只以「程式可以啟動」作為完成標準。

## 10. Agent 工作方式

對複雜任務，必須採取：

探索 → 診斷 → 規劃 → 使用者批准 → 小步驟實作 → 測試 → 回報 → 下一階段

不得自行跳過使用者批准。

不得在沒有測試結果的情況下宣稱完成。

不得為了完成任務而忽略資源限制。

## 11. 回報格式

每次完成工作後，必須回報：

- 本次目標。
- 已檢查的檔案。
- 已修改的檔案。
- 修改原因。
- 測試結果。
- 尚未確認的問題。
- 尚未解決的問題。
- 下一步建議。

如果無法確認原因，必須明確說明。
